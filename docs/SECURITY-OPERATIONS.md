# Security operations and recovery

## Incident review before production release

Source review identified legacy public runtime/push state, public customer photos and overly broad tracking output. This proves risky code paths, not a confirmed production incident. Preserve logs and deployment/version evidence; inspect secret names/storage configuration without fetching public private-key URLs or collecting customer records. Owner must authorize containment and rotation. Disable legacy push, revoke staff/visitor subscriptions and rotate VAPID material if its publication is confirmed or cannot be excluded. Deploy attachment/tracking/marketing boundaries only after backup and legacy rehearsal. Review provider-side Resend audiences, automated events/campaigns and SMS schedules; application suppression cannot cancel previously scheduled provider campaigns. Essential transactional communication remains separate.

## Consistent SQLite and file backups

Production actions below require separate approval. Keep one replica. Stop request acceptance and wait for writes/uploads/background work to finish; stop the app before a whole-volume snapshot. Snapshot the entire `/data` volume, including SQLite WAL/SHM, private files, legacy uploads and published media. Never copy only the main `.db` file from a running WAL database. For an online database-only backup use SQLite's backup API (tested by `tests/recovery.test.mjs`); it includes committed WAL contents. A database-only snapshot does not ensure consistency with concurrent filesystem changes: quiesce all writers for a combined snapshot.

Encrypt backups with independent storage/access, record commit, migration history, UTC capture time, hashes, retention and restoration drill. Never place backups inside the image/static paths, logs or Git. Assign an owner for off-platform storage and scheduled drills. Volume backup availability/retention must be verified with Railway plan and owner.

Restore into an isolated empty volume. Verify hashes, `PRAGMA integrity_check`, `foreign_key_check`, migration history and synthetic counts; test private photo authorization, legacy photos and public media. Rehearse restore before release. Embedded private attachment BLOBs live in SQLite; legacy photos may be embedded data URIs or `/uploads/...` references. Preserve all legacy files and serve them through authenticated compatibility routes. Do not bulk move/delete production photos. Inventory references privately and check missing files without publishing filenames.

### Staging recovery rehearsal

Run `node scripts/rehearse-staging-recovery.mjs` inside the approved staging runtime. The script requires the exact Railway project, environment and service IDs in AGENTS.md, staging mode, and the expected database and upload paths. Prefer a maintenance window before the app starts accepting writes. It opens SQLite read-only, takes an online backup from a consistent read snapshot, hashes the database and media, and verifies a separate restore. It compares booking IDs, tokens, photo references and attachment content by fingerprint. It then tests corrupt and incomplete copies, restoring from its archive before launching a loopback-only app with synthetic fixtures and no provider credentials. Only counts and pass/fail markers are emitted. Each run cleans its temporary copies on normal completion or a handled failure.

For an authorized live staging run, after an SSH key is available to Railway, use the CLI in the explicitly linked staging context or pass exact resource IDs:

### Independent production backup approval gate

Phase 5.4 implements `scripts/portable-backup.mjs` (Node 24, SQLite online backup and system tar). The encrypted `.fmd` file uses AES-256-GCM with a separate random nonce per artifact. The authenticated manifest covers the capture time, exact commit, migration names and checksums, SQLite SHA-256, booking/attachment counts and media hashes. Restore authenticates the envelope before extraction, checks the manifest, SQLite integrity and foreign keys, then removes its disposable directory. Only open artifacts produced by the approved capture tool with a trusted key. Retain the key version in a separate operational inventory.

Live staging deployment `8bfbc965-7bea-43f8-928e-cc8ed3dc01d8` at `bb6e5e1e1568970fd91464f9c6a4e0744334ebf8` produced a 193,065-byte encrypted artifact. Restore reported ten migrations and passed SQLite and restored-application checks. Staging had zero filesystem media files. Separate synthetic tests preserved legacy and CMS hashes, committed WAL, tracking identifiers and attachment bytes and rejected damaged ciphertext, a wrong key and missing restored media. The testing hook was removed from the normal Docker startup.

Agree on the execution identity, maintenance window and encrypted retention destination first. The staging rehearsal command checks staging IDs and must remain staging-only. For production, use a separately reviewed command scoped to the live volume. Record the current deployment and stop booking, attachment, CMS and background writers for the capture window. Open the production SQLite source read-only and use SQLite's online backup API, then copy the full upload tree while writers remain quiesced. Record SQLite checksum, a relative-path media SHA-256 manifest, capture time and migration checksums in the restricted backup. Compare the copied media to the source manifest before reopening writes. Keep paths and record identifiers out of the report.

Production execution sequence after explicit data-access, runtime, maintenance and storage approval:

1. Confirm the exact project/environment/service and volume instance from [PRODUCTION-TRANSITION.md](PRODUCTION-TRANSITION.md). Verify the actual database and media roots match `/data/fixmydoor.db` and `/data/uploads`. They are the production source defaults. Inventory all legacy roots privately before capture. Stop if the source paths differ or expected media is missing. The live application image uses Node 20. Provide an approved temporary Node 24 runtime with the source volume available before the normal app accepts writes, or use an independently approved capture mechanism. Rehearse how to enter and exit maintenance and restore the original start behavior before touching production. Allow enough encrypted ephemeral space for the SQLite copy, media copy, tar and envelope. Do not use the production volume for scratch.
2. Use a user-only scratch directory and inject a raw random 32-byte key as a file with mode 0600. On Windows use a user-only ACL as well. Escrow it in the organization's recovery vault, separately from the ciphertext. Assign two authorized custodians and test retrieval. Use a new key version for future captures if rotation is needed and retain old keys until their last artifact expires. Set `FMD_ALLOW_PRODUCTION_CAPTURE=approved` only in this approved process, and `FMD_WRITERS_QUIESCED=yes` only after stopping every writer. This flag is an assertion, not a write lock. The pre/post media hash comparison is a drift check, not proof of atomicity while writes are active.
3. In that process run `node scripts/portable-backup.mjs capture production /tmp/fmd-private/fixmydoor-UTC.fmd /run/secrets/fmd-backup-key`. The tool requires the exact live IDs and deployment SHA. It opens the source read-only, publishes only a completed encrypted artifact and refuses replacement. Once the capture is made and verified locally, resume the original application and check health. Abort on a failed guard or integrity check. Recover the original startup before investigating prolonged interruption. If forcibly interrupted, remove private scratch using the approved runtime cleanup procedure before resuming a capture.
4. Send only the encrypted object to the approved external bucket using a dedicated backup runner, then download it to independent private scratch with the separate restore credential. Compare SHA-256 with the local encrypted object and run `node scripts/portable-backup.mjs verify disposable fixmydoor-UTC.fmd /run/secrets/fmd-backup-key`. Keep the verified object ID, key version and evidence in the recovery log. Delete temporary copies after verification. Never overwrite the original volume in a drill.

Verify the encrypted artifact by restoring it to an isolated destination with outbound integrations disabled. Check integrity, foreign keys, migration history, protected counts and digests for booking IDs, tracking identifiers and photos. Rehearse the candidate migration on the copy. The new migration creates the Attachment table and indexes with a foreign key to Booking, without rewriting existing booking IDs or photo references. Inventory legacy file and inline references privately, verify staff-only access and published CMS availability, and preserve missing-file handling. Stop on unexplained schema drift, missing required media, or failed integrity checks.

### External backup runner and independent monitor

The Phase 5.5 Railway staging drill ran on commit `8ce71b6af66cc1b31c61046ef5db42566c2e6d5e`, deployment `419cfd0f-5e03-4e62-b35b-74e6ed91be5b`. The loopback S3 fake verified retry and read-back, then the app passed a smoke test against the decrypted restore. SQLite integrity, foreign keys and ten migrations passed. The real provider and its lifecycle enforcement remain unverified. The current staging release uses normal startup.

The Node 24 CLI `scripts/backup-object-store.mjs` uses the AWS S3 SDK with explicit R2 HTTPS endpoints and scoped credentials. It authenticates the source envelope and checks the capture environment before transfer. Every object uses the capture UTC timestamp and encrypted SHA-256. The same artifact keeps its key on retry. Each conditional single PUT can commit only once; a lost response is resolved by checking the object and streaming every byte back through SHA-256 verification. A local download is published only after size and checksum match. Failed transfers have bounded retries and leave no final partial file. Keep the upload input in a runner-owned directory where other processes cannot replace it. Single PUT is capped at 5 GB. Failed or interrupted requests require no multipart cleanup.

Generate separate staging and production keys on an owner-approved, access-restricted runner. `node scripts/backup-object-store.mjs keygen /run/secrets/fmd-backup-key` writes 32 random bytes without printing them and refuses to overwrite an existing key. Use a 0600 file on Linux and a user-only ACL on Windows. Escrow a recoverable copy in an owner-controlled vault outside Railway and record key version against the artifact. Assign two custodians, test vault retrieval, rotate by creating a new key for future archives and retain prior keys until their last retained archive expires. Audit vault access and revoke storage tokens separately from key rotation. A suspected key disclosure requires review of all artifacts encrypted with that version.

After the storage and production capture approvals in [PRODUCTION-TRANSITION.md](PRODUCTION-TRANSITION.md), use short-lived `FMD_S3_WRITE_ID/SECRET/TOKEN` for PutObject and separate `FMD_S3_READ_ID/SECRET/TOKEN` for HeadObject, GetObject and ListObjectsV2. Set `FMD_S3_ENDPOINT` to the approved private R2 API endpoint and `FMD_S3_BUCKET=fixmydoor-production-backups`. Keep these credentials on approved runners or the temporary maintenance process only. Require `FMD_ALLOW_PRODUCTION_TRANSFER=approved` for production commands after the owner authorizes the exact data scope and destination.

For the first real provider test, use a disposable Linux Node 24 runner with the built candidate, Prisma and tar, and only synthetic staging credentials. Set `FMD_S3_BUCKET=fixmydoor-staging-backups`, configure the jurisdiction-specific endpoint and inject the distinct temporary tokens privately. Set `FMD_ALLOW_R2_STAGING_TEST=approved` only after approving the private test bucket. Run `node scripts/verify-r2-staging.mjs /run/secrets/fmd-staging-backup-key <exact-staging-commit>`. The script creates a new temporary migrated SQLite DB, writes synthetic WAL, booking, media and attachment fixtures, uploads and retrieves an encrypted archive, checks anonymous and write-token read denial, and tests the restored app. It never uses the deployed staging or production database. Record the provider result only after observing success. Keep the synthetic objects subject to owner-approved test retention.

For a Windows host with Linux Docker, build the verified checkout and run the same command in a disposable container. Mount only a user-restricted secrets directory from outside the checkout, read-only. Put the approved endpoint, bucket, staging approval flag and temporary R2 sessions in `r2-staging.env` in that directory. Keep the staging key in a separate file there. Use Node's `--env-file` inside the container so Docker container metadata never contains the session values. Copy the key into private Linux scratch with `umask 077` before verification, since Windows bind mounts can present permissive Unix modes. The inventory command reports freshness, while `check` retrieves, authenticates and restores the latest fresh artifact in private scratch before returning success. Missing or older than 36 hours exits 2. Integrity, permission or transfer failures exit 1. Configure the approved independent host scheduler to check at 08:00 UTC daily and alert the owner on either exit or a missing run. Alert on capture failure immediately. Maintain a manual recovery runbook and a periodic independent restore on a separate failure domain. Run `retention-plan production` to review the intended 30-day lifecycle prefix. Apply the rule through an authorized bucket administrator after checking existing lifecycle rules. Confirm expiry metadata after a sandbox upload. The backup runner has no delete or lifecycle permissions.

Railway volumes mount to a service instance at runtime. Railway prevents overlapping active deployments on a service with an attached volume. A second Railway cron service cannot be assumed to share the mounted live database. Railway cron runs its service start command and expects it to exit. For the first capture use an explicitly authorized maintenance window on the attached service with the Node 24 runtime, capture before write acceptance, and re-open the service after the verified encrypted artifact is retained securely. Allow a 120-second capture budget only after a disposable-volume rehearsal establishes a realistic limit and recovery path. Do not repeat redeploys daily. For recurring capture, design a single-flight in-container job after the security release with a bounded write gate for booking, attachment, CMS and background writers. Only capture needs the write gate. Upload after reopening writers from private scratch, with an independent maximum runtime. The capture command's quiesced flag is an operator assertion. Automated capture stays disabled until the write gate and crash recovery are implemented and tested. Phase 5.6 exercised a one-shot boot scheduler on staging. The gate shared one attempt per process and enforced a 110-second child process budget. Logs show `STAGING_GATE_WRITERS_OFFLINE`, the successful local S3-compatible recovery, gate release and only then the app listener. This is a full process stop/start boundary, so it does not rely on per-route middleware covering every possible writer. For an approved maintenance capture, allow current requests to drain before stopping the old instance, communicate brief unavailability, and abort if the drain or capture exceeds the approved window. The test protects the offline path. It does not establish daily capture against an already running application.

Phase 5.7 adds a staging-only online drill on the single volume-owning service. Its gate pauses the authenticated CMS media upload route, which is the only application filesystem writer to the upload tree. The route returns a retryable 503 and leaves media unchanged. The write itself is synchronous, so it cannot straddle the in-process gate. Bookings and private attachments stay in SQLite and continue on WAL while the online backup takes a consistent SQLite snapshot. Admin CMS record writes can reference either an existing file or a future upload. Before any production rollout, audit references for missing files and reconfirm the app is the only volume writer. The gate does not cover another process or manual file edits.

The child capture has a 30-second deadline and the media gate releases on close or failure. Decrypt, integrity and restored-app verification run after the gate opens. A test proves duplicate capture rejection, a booking write during the gate, restored booking/media counts, and release on error. Use the existing external `inventory` and `check` commands to detect missing, stale or unverifiable objects. Production recurring capture remains disabled. Before enabling a daily job, confirm the provider test, runner credentials, timing and alert routing, and reassess any added filesystem writer.

### Evidence review and provider checks

With owner-approved access, preserve applicable deployment revisions and metadata, then review selected historic request logs locally for runtime file, subscription, upload and tracking routes. Record UTC ranges, HTTP outcomes, response metadata and aggregation limits. Redact tokens, addresses and other personal data. A successful request alone does not establish which data was delivered. If VAPID private material was exposed or exposure cannot be ruled out, coordinate revocation of affected subscriptions and rotation with the owner. Rotate other credentials only if the evidence calls for it.

In Resend, review scheduled Broadcasts, active Automations and their event triggers, audience segments and suppression rules. Identify campaigns triggered by a booking, status change, contact sync or content publication. Obtain approval to pause promotional broadcasts and automations or exclude contacts lacking marketing consent. Preserve opt-outs and transactional booking and service updates. Record the reviewed items and outstanding owner actions without exporting contact lists or sending messages.

## Rollback

Record current deployment image and exact application revision. Restore code only when schema remains compatible. If migration/data incompatibility exists, stop writes and restore the consistent pre-release volume to an isolated replacement before switching traffic under owner approval. Preserve failed-release evidence. Do not blindly overwrite newer customer requests with an older backup; reconcile post-backup writes under a documented recovery decision. Set RPO/RTO and retention with the owner.
